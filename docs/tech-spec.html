HOSPITAL-CHAIN DEMOTECHNICAL SPECIFICATIONEXASOL 2026.2.0-nano.3

One patient, every branch: how the hospital-chain demo is built

A hospital chain with an old hospital information system on Postgres, a modern electronic health record on MongoDB and an imaging archive on Amazon S3. Exasol reads all three where they are, ties the records to one person, applies one set of rules, and answers in about a second. This document explains every part: what each database holds, how Exasol connects to it, how a query travels, and how an image gets from S3 to the screen.

The story. Mrs Meenakshi Sundaram, 68, diabetic, was treated in Branch A in 2019 and had anaphylaxis to IV amoxicillin-clavulanate. That fact is free text in the Branch A legacy system. Today she is admitted in Branch B, whose modern EHR has no allergy on file, and the doctor drafts amoxicillin-clavulanate. Neither system can see the conflict. Exasol can, because it reads both live and knows the two records are the same person.

What is real and what is synthetic. The patients, visits, orders and notes are synthetic, generated with a fixed seed (today is fixed at 2026-10-26). The images are real, de-identified studies from The Cancer Imaging Archive (COVID-19-AR chest X-ray/CT and UPENN-GBM brain MRI, CC BY 4.0), relabelled to the synthetic patients. The databases, the S3 bucket, the virtual schemas, the MCP server and the users are all real and running.

Why the sources run inside the Exasol VM

The first build ran Postgres and MongoDB in Docker on the Mac. A managed laptop firewall that blocks inbound connections to every app, so the VM could open a TCP connection to a Docker port but was cut off immediately. Moving both sources into podman inside the VM puts them on the same host as the database: Exasol reaches them through the podman bridge gateway 10.88.0.1, and the Mac reaches them outbound on the VM's IP. In a customer deployment the sources would simply be other hosts on the network, reached the same way.

After the VM restarts the containers do not come back on their own (the VM has no systemd), and the VM clock can freeze after the Mac sleeps, which makes S3 refuse signed requests with 403. setup/preflight.sh fixes both.

04How Exasol connects

Exasol reaches outside systems through three building blocks. Each is a database object, so access to it is granted and audited like any other object.

CONNECTION

A named, stored address plus credentials. Users can be allowed to use a connection without ever seeing the secret inside it.

Adapter script

A program (Java for Postgres, Rust for MongoDB) that runs inside Exasol. It answers two questions: what tables exist at the source, and how to fetch what a query needs.

Virtual schema

A schema whose tables look local but have no data. Every query against it is handed to the adapter, which rewrites it into a fetch from the source.

05Virtual schema: Postgres (legacy HIS)

The official Exasol PostgreSQL virtual schema (JDBC dialect 4.0.1 on the virtual-schema framework 14.0.4).

CREATE OR REPLACE JAVA ADAPTER SCRIPT HOSP_ADAPTERS.POSTGRES_ADAPTER AS
  %scriptclass com.exasol.adapter.RequestDispatcher;
  %jvmoption -Duser.timezone=UTC;                       -- without it, DATE values shift by the VM's offset
  %jar /buckets/bfsdefault/default/hospital/jars/virtual-schema-dist-14.0.4-postgresql-4.0.1.jar;
  %jar /buckets/bfsdefault/default/hospital/jars/postgresql-42.7.4.jar;
/
CREATE VIRTUAL SCHEMA HOSP_LEGACY USING HOSP_ADAPTERS.POSTGRES_ADAPTER WITH
  CONNECTION_NAME = 'HOSP_LEGACY_PG'  CATALOG_NAME = 'branch_a_his'  SCHEMA_NAME = 'his'
  POSTGRESQL_IDENTIFIER_MAPPING = 'CONVERT_TO_UPPER';   -- his.pat_mstr appears as HOSP_LEGACY.PAT_MSTR

What happens when it is created

Exasol calls the adapter with a create request. The adapter connects with the JDBC driver, reads Postgres's catalog for schema his, and returns the table and column list with Exasol types (VARCHAR(20), DECIMAL(5,0) and so on). Exasol stores that metadata. No rows are read. If the Postgres schema changes, ALTER VIRTUAL SCHEMA HOSP_LEGACY REFRESH re-reads it.

What happens on every query

  1. Exasol parses the SQL and finds the part that touches HOSP_LEGACY tables.
  2. It sends the adapter a pushdown request: a JSON description of that part (tables, needed columns, filters, the adapter's capabilities).
  3. The adapter writes Postgres SQL for as much as Postgres can do (column selection, filters, LIKE, joins inside the same source, aggregates where allowed) and wraps it in an IMPORT FROM JDBC statement.
  4. Exasol's loader runs that statement: it opens a JDBC connection with the stored credentials, executes the SQL on Postgres and streams the rows in parallel.
  5. Exasol joins the result with everything else in the query (MongoDB data, the patient index) in memory.

A real example: the hero's allergy note. EXPLAIN VIRTUAL shows exactly what Postgres received:

IMPORT INTO (c1 VARCHAR(20) UTF8, c2 VARCHAR(2000000) UTF8) FROM JDBC AT HOSP_LEGACY_PG
STATEMENT 'SELECT "s"."visit_no", "s"."summ_txt" FROM "his"."dis_summ" "s"
           WHERE "s"."summ_txt" LIKE E''%ANAPHYLAXIS%'''          -- the filter ran in Postgres

IMPORT INTO (c1 VARCHAR(20) UTF8, c2 VARCHAR(20) UTF8, c3 VARCHAR(10) UTF8) FROM JDBC AT HOSP_LEGACY_PG
STATEMENT 'SELECT "v"."visit_no", "v"."pat_no", "v"."adm_dt" FROM "his"."visit_hdr" "v"'
                                                                   -- only 3 columns; the join to the patient index ran in Exasol

Only the needed columns cross the wire, and filters run at the source. A join between a source table and something that lives in Exasol (here the patient index) cannot be pushed, so Exasol fetches the narrow column set and joins locally. The console's "For engineers" panel shows this live for questions 1, 2, 5 and 6.

Function support matters. The dialect pushes many expressions down. REGEXP_LIKE is one of them, but Postgres has no such function, so the query fails at the source. The typed views therefore use LIKE on legacy columns, and keep REGEXP_SUBSTR for parts the adapter evaluates in Exasol.

What happens on every query

Unlike Postgres, MongoDB does not speak SQL, so the adapter does not write a statement for the source. It answers the pushdown request with a call to a scan UDF that runs inside Exasol. The UDF gets a JSON plan, connects to MongoDB with the stored credentials, runs a find with the filter applied in MongoDB, and emits rows. A real plan for "encounters in progress":

SELECT "mongo_id", "status" FROM (
  SELECT MONGODB_VS.MONGODB_SCAN('{
    "connection_name": "HOSP_MODERN_MONGO", "database": "ehr", "collection": "encounters",
    "plan": { "kind": "root_find" },
    "columns": [ { "source": {"kind":"field","name":"_id"},    "exasol_name": "mongo_id" },
                 { "source": {"kind":"field","name":"status"}, "exasol_name": "status" } ],
    "batch_size": 128,
    "pushdown": { "prefilter": { "kind":"compare", "op":"equal", "column":"status",
                                 "literal": {"kind":"string","value":"in-progress"} } },
    "inference_fingerprint": "c465f23a…" }')
  EMITS ("mongo_id" VARCHAR(2000000), "status" VARCHAR(2000000)))

Only the two needed fields are projected, and status = 'in-progress' becomes a MongoDB filter. The inference_fingerprint ties the plan to the inferred schema, so a stale schema is detected rather than silently misread.

For the PACS no virtual schema is needed: Exasol's IMPORT can read a file straight from S3, and putting it inside a view makes it read on every query.

CREATE OR REPLACE VIEW HOSP_SRC.IMAGING_INDEX AS
SELECT * FROM (
  IMPORT INTO (PATIENT_ID VARCHAR(40), PATIENT_NAME VARCHAR(80), … , S3_KEY VARCHAR(200), THUMB_KEY VARCHAR(120))

CSV, not Parquet. A Parquet copy of the index sits beside the CSV. On this Personal build the Parquet reader adds a fixed ~12 s to every request to an amazonaws.com host (even for a missing file), so the view reads the CSV. Worth reporting to Exasol.

09Patient index (MPI)

The master patient index decides which records are the same person. It is plain SQL with deterministic rules (sql/20_mpi.sql): no model, nothing to train, and a written reason on every link.

  1. Collect. PATIENT_RECORDS = every legacy and modern patient record, read live through the typed views (874 + 735 = 1,609).
  2. Block. Only compare pairs that share sex and one strong key (the given name sounds alike, the same mobile, or the same birth date). Pairs inside the EHR, and legacy pairs within the same branch, are skipped. This keeps the comparison far smaller than a full cross join.
  3. Score each pair:
    SignalPoints
    Given name exact / sounds alike (SOUNDEX) or within 2 edits25 / 15
    Surname exact (more than an initial) / same first letter / differs15 / 10 / −15
    Birth date exact / day and month swapped / no date but age within 1 year35 / 25 / 10
    Mobile exact30
  4. Decide. Score ≥ 70: linked automatically. 55–69: MATCH_REVIEW_QUEUE, never auto-linked. Below 55: different people.
  5. Anchor. The modern EHR record anchors the person. A legacy record joins its best-scoring modern record; a legacy record whose twin at another branch is linked to a modern record follows it (transitive). People with no modern record are anchored on their lowest legacy ID.
  6. Number. UNIFIED_ID = 'UP-' || LPAD(DENSE_RANK() OVER (ORDER BY anchor), 6, '0'). Also PACS_PATIENT_ID = REPLACE(RECORD_ID, '/', ''), which is how the scanners write the ID into DICOM.

The hero: BRA/2014/000731 (MEENAKSHI S, 14/03/1958) ↔ BRB-P-108842 (Meenakshi Sundaram, 1958-03-14) scores 25 + 10 + 35 + 30 = 100: "given name exact · surname initial agrees · birth date exact · mobile exact". Her DICOM files tagged BRA2014000731 and BRB-P-108842 both resolve to the same UNIFIED_ID.

Measured quality (data/check_mpi.py against the truth file): 1,609 records → 1,224 people, precision 100% (no wrong merge), recall 94.3% (the rest are records the rules deliberately leave apart, several of them in the review queue). In a hospital, a wrong merge is worse than a missed link, so the threshold is set for precision.

Refresh. The index is a stored table built from live data. In this demo it is built at set-up; in production it would rebuild nightly or on each new registration. Everything else reads it live.

The allergy safety check (HOSP_CORE.ALLERGY_CONFLICTS)

SELECT o.UNIFIED_ID, o.ENCOUNTER_ID, o.SOURCE_SYSTEM AS PRESCRIBED_IN, o.DRUG, o.DOSE, o.ORDER_STATUS, o.DRUG_CLASS,

FROM HOSP_CORE.MEDICATIONS o                                   -- orders from BOTH systems, + drug class
JOIN HOSP_CORE.ALLERGIES a ON a.UNIFIED_ID = o.UNIFIED_ID       -- same PERSON, any system
                           AND a.DRUG_CLASS = o.DRUG_CLASS
WHERE o.ORDER_STATUS IN ('draft', 'active');

KNOWN_WHERE_PRESCRIBED = FALSE means the allergy is filed under a different record than the order, so the prescribing system had no way to see it. Today: 3 patients in a bed have such an order (Meenakshi Sundaram and Usha Kulkarni, registered in Branch B, and Thomas Patil in Branch C), and in all 3 cases the allergy is only in the legacy system.

30-day readmission (HOSP_CORE.READMISSIONS_30D)

An inpatient admission within 0–30 days of the same person's previous inpatient discharge, at any branch, in any system. Computed with LAG(DISCHARGE_DATE) OVER (PARTITION BY UNIFIED_ID ORDER BY ADMIT_DATE). VISIBLE_TO_ONE_SYSTEM is true when the previous stay is under the same record ID, meaning a branch system on its own would have counted it. Result: 462 readmissions, 148 of them (32%) invisible to any single system.

Diabetes in either system

The EHR codes diabetes (E11*); the legacy HIS never did, but it ordered HbA1c tests. DIABETIC_PATIENTS takes either signal, which is how question 4 finds diabetic patients across both systems.

11Note vectors and "patients like her"

3,976 clinical notes (2,234 legacy discharge summaries + EHR admission notes) were embedded once with BAAI/bge-small-en-v1.5 (384 dimensions, via fastembed), normalised to length 1, and stored long and narrow:

HOSP_CORE.NOTE_INDEX   (NOTE_ID, SOURCE_SYSTEM, RECORD_ID, ENCOUNTER_ID)   -- one row per note
HOSP_CORE.NOTE_VECTORS (NOTE_ID, DIM, VAL)                                 -- 384 rows per note = 1,526,784 rows

Because the vectors are unit length, cosine similarity is just a dot product, and a dot product is a join plus a GROUP BY. No vector type and no UDF in the hot path:

WITH q AS (SELECT DIM, VAL FROM HOSP_CORE.NOTE_VECTORS WHERE NOTE_ID = 'M:ENC-BRB-2610-02605'),   -- her note today
sim AS (SELECT v.NOTE_ID, SUM(v.VAL * q.VAL) AS SIMILARITY
        FROM HOSP_CORE.NOTE_VECTORS v JOIN q ON q.DIM = v.DIM GROUP BY v.NOTE_ID)
…  -- then: diabetic in either system, over 60, penicillin allergy in either system, + antibiotic, stay, readmission

Load details (data/embed.py): notes are read from data/out/notes.csv (written by the generator from both systems), lower-cased, embedded in batches of 64 as float32, L2-normalised, rounded to 6 decimals, and loaded with pyexasol import_from_pandas (compressed) into NOTE_INDEX (NOTE_ID, SOURCE_SYSTEM, RECORD_ID, ENCOUNTER_ID, MODEL) and NOTE_VECTORS (NOTE_ID VARCHAR(40), DIM DECIMAL(4,0), VAL DOUBLE). HOSP_CORE.NOTES ties each note to its person through the MPI.

The note text stays in its source; Exasol keeps only the key and the numbers. For free text typed in the console, the same model embeds the text (about 2 s, in a subprocess of the project's Python environment) and the 384 numbers go into the query as a VALUES list. The whole question takes about 4 s.

12How images are read and shown

The rule: the database handles facts about images, never pixels. Exasol finds which files belong to the patient; the bytes go straight from S3 to whoever displays them.

Two separate reads: metadata by Exasol, pixels by the viewer

1 · Exasol reads metadata

One small file, index/dicom_index.csv, sits next to the images. It has one row per study, holding the values from that DICOM file's header plus the file's S3 location. Exasol reads it live on every query (IMPORT … FROM CSV AT HOSP_S3, one signed GET, about 0.3 s), matches PATIENT_ID to the patient index and returns her rows. It never opens a .dcm file.

2 · The viewer reads pixels

The console takes S3_KEY / THUMB_KEY from those rows and signs a 15-minute link with the read-only IAM user. The browser downloads the PNG preview straight from S3. For "Render it from the DICOM file now", the console downloads the original .dcm file itself, reads its header with pydicom and turns the pixels into a PNG. Exasol is not involved in either case.

How Exasol finds which files belong to her

A three-step join. Nothing is searched inside the images.

  1. Start from the person. The patient index says she is UP-000816 and lists every record she has: BRA/2014/000731 (Branch A, legacy HIS) and BRB-P-108842 (Branch B, EHR).

Where the metadata file comes from

data/imaging.py wrote it once, when the images were archived: for each DICOM file it read the header with pydicom, wrote one CSV row and uploaded the file to S3 (a Parquet copy sits beside it, not used; see section 07). Every real PACS keeps the same list in its own database, so studies can be searched without opening files. In production Exasol would read that list, through a virtual schema on the PACS database, a DICOMweb (QIDO-RS) query or a regular export like this one, instead of a file we generated.

Why metadata, not the files

  • Fast: one small file answers "which scans belong to her" in 0.3 s. Opening 168 DICOM files (139 MB) on every question would take far longer.
  • Safe: no pixel data passes through or is stored in the database. The image goes from S3 only to the authorised viewer, by a link that expires.
  • Realistic: search on metadata, then open the image in a viewer. Hospitals already work this way.
Alternative, not used here: a Python UDF in Exasol could open each .dcm in S3 and read the header directly, so no separate index would be needed. It works, but it is slower and duplicates what the PACS already keeps.

Why signed URLs

The bucket is private. A presigned URL is a normal HTTPS link with the signature in the query string (X-Amz-Algorithm=AWS4-HMAC-SHA256, X-Amz-Credential, X-Amz-Expires=900, X-Amz-Signature). It grants one GET of one object for 15 minutes. It must be signed for the regional endpoint (s3.ap-south-1.amazonaws.com) with SigV4; the global endpoint signs for us-east-1 and S3 answers SignatureDoesNotMatch.

How the previews were made

Offline, once, by data/imaging.py: download the TCIA series, take the middle frame of multi-frame studies, apply the VOI LUT, clip to the 0.5–99.5 percentile, relabel every identifying tag (PatientID, name, birth date, dates, institution, accession number, new UIDs, PatientIdentityRemoved = YES), write the 768 px DICOM and a 420 px PNG, upload both, and write the index row. The console links three ways to each file: the s3:// URI, the AWS console page, and a signed download.

In production a hospital would put a DICOM viewer (OHIF or the PACS's own) behind the same signed-link pattern, or use DICOMweb (WADO-RS). Exasol's role is unchanged: find the right studies for the right person, under the caller's access rules.

21Questions to expect

Is any patient data copied into Exasol?
Only what earns it: the patient index (record IDs, names and birth dates needed for matching), the note vectors (numbers, not text), and the optional copy of encounters for the readmission question. Every other answer reads the sources live.
How fresh is the data?
Live for orders, allergies, encounters and images: a draft order written in MongoDB a second ago is in the next answer. The patient index and the note vectors are as fresh as their last rebuild (nightly or on each registration in production).
What does the source system actually receive?
Postgres receives ordinary SELECTs with only the needed columns and the filters (section 05, visible with EXPLAIN VIRTUAL). MongoDB receives a find with a projection and a filter (section 06). S3 receives one GET for the index.
What if a source is down?
Questions that need it fail with a clear error; others keep working. The console shows the last good result, labelled as cached. In production, the questions that must survive an outage are the ones to copy into HOSP_ACCEL.
Can it write back to the HIS or EHR?
No, by design. Every connection uses a read-only login at the source.
How do you stop a wrong merge of two patients?
The threshold favours precision (100% here), every link carries its reason, and borderline pairs go to a review queue instead of being merged. Rules are SQL, so a clinician-approved change is a reviewed diff.
Why not migrate everything first?
Because answers are needed now and migrations take years. Federation gives the answer on day one; the copy is added for the paths that prove worth it; migration can happen later, branch by branch, without changing the views people use.
Does the AI see raw patient data?
It sees exactly what the person it acts for may see: the same governed views, the same row filter, the same masking, the same audit log. Asking for the raw table is refused by the database, not by the prompt.
How would this scale to a real chain?
Exasol runs as a cluster; the virtual schemas push work to the sources; the patient index and vectors are ordinary tables. The demo's laptop limits (one VM, 20 connections) are not product limits.
Where would the images be viewed in production?
In the hospital's DICOM viewer, opened with the same signed-link or DICOMweb pattern. Exasol's part is finding the right studies for the right person under the caller's rules.

sql/10_typed_sources.sql

-- LIKE, not REGEXP_LIKE: the Postgres dialect pushes these expressions down and Postgres has no REGEXP_LIKE.
-- HOSP_SRC: the sources, read live, translated into one vocabulary. Views only: nothing is stored.
-- Every view reads a virtual schema (Postgres legacy HIS, MongoDB modern EHR) on each query.
CREATE SCHEMA IF NOT EXISTS HOSP_SRC;

-- ---------------------------------------------------------------- legacy HIS (Postgres): text dates, initials, free text
CREATE OR REPLACE VIEW HOSP_SRC.LEGACY_PATIENTS AS
WITH raw AS (
  SELECT p.PAT_NO, p.BRANCH_CD, p.PAT_NM, p.SEX, p.DOB_TXT, p.AGE_YRS, p.PH_NO, p.CITY,
         REGEXP_SUBSTR(p.PAT_NM, '[^ ]+', 1, 1) AS T1, REGEXP_SUBSTR(p.PAT_NM, '[^ ]+', 1, 2) AS T2
  FROM HOSP_LEGACY.PAT_MSTR p)
SELECT PAT_NO AS RECORD_ID, 'LEGACY_HIS' AS SOURCE_SYSTEM, BRANCH_CD AS BRANCH, PAT_NM AS NAME_AS_RECORDED,
       CASE WHEN LENGTH(REPLACE(T1, '.', '')) <= 1 THEN T2 ELSE T1 END AS GIVEN_NAME,
       CASE WHEN LENGTH(REPLACE(T1, '.', '')) <= 1 THEN REPLACE(T1, '.', '') ELSE T2 END AS FAMILY_NAME,   -- often only an initial
       SEX,
       CASE WHEN DOB_TXT LIKE '__/__/____' THEN TO_DATE(DOB_TXT, 'DD/MM/YYYY')
            WHEN DOB_TXT LIKE '__-__-__' THEN TO_DATE(SUBSTR(DOB_TXT, 1, 6)
                 || CASE WHEN CAST(SUBSTR(DOB_TXT, 7, 2) AS DECIMAL(2,0)) >= 27 THEN '19' ELSE '20' END || SUBSTR(DOB_TXT, 7, 2), 'DD-MM-YYYY')
       END AS BIRTH_DATE,
       -- the same text read the other way round: front desks swap day and month when both are <= 12
       CASE WHEN DOB_TXT LIKE '__/__/____' AND CAST(SUBSTR(DOB_TXT, 1, 2) AS DECIMAL(2,0)) <= 12
             AND CAST(SUBSTR(DOB_TXT, 4, 2) AS DECIMAL(2,0)) <> CAST(SUBSTR(DOB_TXT, 1, 2) AS DECIMAL(2,0))
            THEN TO_DATE(DOB_TXT, 'MM/DD/YYYY') END AS BIRTH_DATE_SWAPPED,
       DOB_TXT AS BIRTH_DATE_AS_RECORDED, AGE_YRS AS AGE_ONLY,
       -- a 10-digit Indian mobile starts with 6-9; 0000xxxxxx is this demo's synthetic, undiallable range
       CASE WHEN LENGTH(PH_NO) = 10 AND (SUBSTR(PH_NO, 1, 1) IN ('6', '7', '8', '9') OR PH_NO LIKE '0000%') THEN PH_NO END AS MOBILE,
       INITCAP(CITY) AS CITY
FROM raw;

CREATE OR REPLACE VIEW HOSP_SRC.LEGACY_ENCOUNTERS AS
SELECT v.VISIT_NO AS ENCOUNTER_ID, v.PAT_NO AS RECORD_ID, 'LEGACY_HIS' AS SOURCE_SYSTEM, v.BRANCH_CD AS BRANCH,
       CASE v.VISIT_TYP WHEN 'IP' THEN 'inpatient' WHEN 'ER' THEN 'emergency' ELSE 'outpatient' END AS ENCOUNTER_CLASS,
       CASE v.DEPT_CD WHEN 'PULM' THEN 'Pulmonology' WHEN 'CARD' THEN 'Cardiology' WHEN 'NEURO' THEN 'Neurology'
            WHEN 'MED' THEN 'General Medicine' WHEN 'ENDO' THEN 'Endocrinology' WHEN 'ONCO' THEN 'Oncology'
            WHEN 'ORTHO' THEN 'Orthopaedics' ELSE 'Emergency' END AS DEPARTMENT,
       TO_DATE(v.ADM_DT, 'DD/MM/YYYY') AS ADMIT_DATE, TO_DATE(v.DIS_DT, 'DD/MM/YYYY') AS DISCHARGE_DATE,
       'finished' AS STATUS, v.DX_CD AS DX_CODE, INITCAP(v.DX_DESC) AS DIAGNOSIS
FROM HOSP_LEGACY.VISIT_HDR v;

CREATE OR REPLACE VIEW HOSP_SRC.LEGACY_ALLERGIES AS
SELECT a.PAT_NO AS RECORD_ID, 'LEGACY_HIS' AS SOURCE_SYSTEM, a.ALRGY_NOTE AS ALLERGY_AS_RECORDED,
       CASE WHEN (UPPER(a.ALRGY_NOTE) LIKE '%PENICILLIN%' OR UPPER(a.ALRGY_NOTE) LIKE '%AMOXY%' OR UPPER(a.ALRGY_NOTE) LIKE '%AMPICILLIN%' OR UPPER(a.ALRGY_NOTE) LIKE '%PEN ALLERGY%' OR UPPER(a.ALRGY_NOTE) LIKE '%BETA-LACTAM%') THEN 'PENICILLIN'
            WHEN (UPPER(a.ALRGY_NOTE) LIKE '%SULPHA%' OR UPPER(a.ALRGY_NOTE) LIKE '%SULFA%') THEN 'SULFONAMIDE'
            WHEN (UPPER(a.ALRGY_NOTE) LIKE '%NSAID%' OR UPPER(a.ALRGY_NOTE) LIKE '%IBUPROFEN%' OR UPPER(a.ALRGY_NOTE) LIKE '%DICLOFENAC%') THEN 'NSAID'
            WHEN (UPPER(a.ALRGY_NOTE) LIKE '%CEFTRIAXONE%' OR UPPER(a.ALRGY_NOTE) LIKE '%CEPHALO%') THEN 'CEPHALOSPORIN' END AS DRUG_CLASS,
       CASE WHEN (UPPER(a.ALRGY_NOTE) LIKE '%ANAPHYLAXIS%' OR UPPER(a.ALRGY_NOTE) LIKE '%STEVENS%' OR UPPER(a.ALRGY_NOTE) LIKE '%ANGIOEDEMA%' OR UPPER(a.ALRGY_NOTE) LIKE '%BRONCHOSPASM%') THEN 'severe' ELSE 'moderate' END AS SEVERITY
FROM HOSP_LEGACY.ALRGY_TXT a
WHERE UPPER(a.ALRGY_NOTE) NOT IN ('NKDA', 'NO KNOWN ALLERGY', 'NIL');

CREATE OR REPLACE VIEW HOSP_SRC.LEGACY_MEDICATIONS AS
SELECT r.VISIT_NO AS ENCOUNTER_ID, v.PAT_NO AS RECORD_ID, 'LEGACY_HIS' AS SOURCE_SYSTEM, INITCAP(r.DRUG_NM) AS DRUG,
       r.DOSE_TXT AS DOSE, 'completed' AS ORDER_STATUS
FROM HOSP_LEGACY.RX_LINE r JOIN HOSP_LEGACY.VISIT_HDR v ON v.VISIT_NO = r.VISIT_NO;

-- ---------------------------------------------------------------- modern EHR (MongoDB): nested documents become child tables
CREATE OR REPLACE VIEW HOSP_SRC.MODERN_PATIENTS AS
SELECT p."mongo_id" AS RECORD_ID, 'MODERN_EHR' AS SOURCE_SYSTEM, p."homeBranch" AS BRANCH, n."text" AS NAME_AS_RECORDED,
       UPPER(n."given") AS GIVEN_NAME, UPPER(n."family") AS FAMILY_NAME,
       CASE p."gender" WHEN 'female' THEN 'F' WHEN 'male' THEN 'M' END AS SEX,
       TO_DATE(p."birthDate", 'YYYY-MM-DD') AS BIRTH_DATE, p."birthDate" AS BIRTH_DATE_AS_RECORDED,
       RIGHT(t."mobile", 10) AS MOBILE, a."city" AS CITY, p."allergies|array" AS ALLERGIES_RECORDED
FROM HOSP_EHR_PATIENTS.PATIENTS p
LEFT JOIN HOSP_EHR_PATIENTS."PATIENTS_name" n ON n."_id" = p."name|object"
LEFT JOIN HOSP_EHR_PATIENTS."PATIENTS_telecom" t ON t."_id" = p."telecom|object"
LEFT JOIN HOSP_EHR_PATIENTS."PATIENTS_address" a ON a."_id" = p."address|object";

CREATE OR REPLACE VIEW HOSP_SRC.MODERN_CONDITIONS AS
SELECT p."mongo_id" AS RECORD_ID, c."code" AS CONDITION_CODE, c."display" AS CONDITION_NAME
FROM HOSP_EHR_PATIENTS."PATIENTS_conditions_arr" c JOIN HOSP_EHR_PATIENTS.PATIENTS p ON p."_id" = c."_parent";

CREATE OR REPLACE VIEW HOSP_SRC.MODERN_ALLERGIES AS
SELECT p."mongo_id" AS RECORD_ID, 'MODERN_EHR' AS SOURCE_SYSTEM, al."substance" || ' (' || al."reaction" || ')' AS ALLERGY_AS_RECORDED,
       CASE WHEN (UPPER(al."substance") LIKE '%PENICILLIN%' OR UPPER(al."substance") LIKE '%AMOXY%' OR UPPER(al."substance") LIKE '%AMPICILLIN%') THEN 'PENICILLIN'
            WHEN (UPPER(al."substance") LIKE '%SULPHA%' OR UPPER(al."substance") LIKE '%SULFA%' OR UPPER(al."substance") LIKE '%SULFONAMIDE%') THEN 'SULFONAMIDE'
            WHEN (UPPER(al."substance") LIKE '%NSAID%' OR UPPER(al."substance") LIKE '%IBUPROFEN%' OR UPPER(al."substance") LIKE '%DICLOFENAC%') THEN 'NSAID'
            WHEN (UPPER(al."substance") LIKE '%CEFTRIAXONE%' OR UPPER(al."substance") LIKE '%CEPHALO%') THEN 'CEPHALOSPORIN' END AS DRUG_CLASS,
       al."severity" AS SEVERITY
FROM HOSP_EHR_PATIENTS."PATIENTS_allergies_arr" al JOIN HOSP_EHR_PATIENTS.PATIENTS p ON p."_id" = al."_parent";

CREATE OR REPLACE VIEW HOSP_SRC.MODERN_ENCOUNTERS AS
SELECT e."mongo_id" AS ENCOUNTER_ID, e."patientId" AS RECORD_ID, 'MODERN_EHR' AS SOURCE_SYSTEM, e."branch" AS BRANCH,
       e."class" AS ENCOUNTER_CLASS, e."department" AS DEPARTMENT,
       TO_DATE(SUBSTR(e."admitted", 1, 10), 'YYYY-MM-DD') AS ADMIT_DATE, TO_DATE(e."discharged", 'YYYY-MM-DD') AS DISCHARGE_DATE,

-- HOSP_CORE: the master patient index. One person, many records: legacy HIS (per branch) + modern EHR + PACS.
-- Rebuilt from the LIVE sources by this script (in production: nightly, or on every new registration).
-- Deterministic rules, every link explained in MATCH_REASON. No model, nothing to retrain.

-- 1. every patient record the chain holds, read live from Postgres and MongoDB
CREATE OR REPLACE TABLE HOSP_CORE.PATIENT_RECORDS AS
SELECT RECORD_ID, SOURCE_SYSTEM, BRANCH, NAME_AS_RECORDED, GIVEN_NAME, FAMILY_NAME, SEX, BIRTH_DATE, BIRTH_DATE_SWAPPED,
       BIRTH_DATE_AS_RECORDED, AGE_ONLY, MOBILE, CITY
FROM HOSP_SRC.LEGACY_PATIENTS
UNION ALL
SELECT RECORD_ID, SOURCE_SYSTEM, BRANCH, NAME_AS_RECORDED, GIVEN_NAME, FAMILY_NAME, SEX, BIRTH_DATE, CAST(NULL AS DATE),
       BIRTH_DATE_AS_RECORDED, CAST(NULL AS DECIMAL(4,0)), MOBILE, CITY
FROM HOSP_SRC.MODERN_PATIENTS;

-- 2. score candidate pairs (blocked on sex + one strong key, so this is not a full cross join)
CREATE OR REPLACE TABLE HOSP_CORE.MATCH_CANDIDATES AS
WITH pairs AS (
  SELECT a.RECORD_ID AS A_ID, b.RECORD_ID AS B_ID, a.SOURCE_SYSTEM AS A_SYS, b.SOURCE_SYSTEM AS B_SYS,
    CASE WHEN a.GIVEN_NAME = b.GIVEN_NAME THEN 25
         WHEN SOUNDEX(a.GIVEN_NAME) = SOUNDEX(b.GIVEN_NAME) OR EDIT_DISTANCE(a.GIVEN_NAME, b.GIVEN_NAME) <= 2 THEN 15 ELSE 0 END AS S_GIVEN,
    CASE WHEN a.FAMILY_NAME = b.FAMILY_NAME AND LENGTH(a.FAMILY_NAME) > 1 THEN 15
         WHEN SUBSTR(a.FAMILY_NAME, 1, 1) = SUBSTR(b.FAMILY_NAME, 1, 1) THEN 10 ELSE -15 END AS S_FAMILY,
    CASE WHEN a.BIRTH_DATE = b.BIRTH_DATE THEN 35
         WHEN a.BIRTH_DATE_SWAPPED = b.BIRTH_DATE OR b.BIRTH_DATE_SWAPPED = a.BIRTH_DATE THEN 25
         WHEN (a.BIRTH_DATE IS NULL AND ABS(a.AGE_ONLY - YEARS_BETWEEN(CURRENT_DATE, b.BIRTH_DATE)) <= 1)
           OR (b.BIRTH_DATE IS NULL AND ABS(b.AGE_ONLY - YEARS_BETWEEN(CURRENT_DATE, a.BIRTH_DATE)) <= 1) THEN 10
         ELSE 0 END AS S_BIRTH,
    CASE WHEN a.MOBILE = b.MOBILE THEN 30 ELSE 0 END AS S_MOBILE,
    CASE WHEN a.BIRTH_DATE_SWAPPED = b.BIRTH_DATE OR b.BIRTH_DATE_SWAPPED = a.BIRTH_DATE THEN 1 ELSE 0 END AS SWAPPED,
    CASE WHEN a.BIRTH_DATE IS NULL OR b.BIRTH_DATE IS NULL THEN 1 ELSE 0 END AS AGE_ONLY
  FROM HOSP_CORE.PATIENT_RECORDS a
  JOIN HOSP_CORE.PATIENT_RECORDS b
    ON a.SEX = b.SEX AND a.RECORD_ID < b.RECORD_ID
   AND NOT (a.SOURCE_SYSTEM = 'MODERN_EHR' AND b.SOURCE_SYSTEM = 'MODERN_EHR')           -- the EHR is one database: no duplicates inside it
   AND NOT (a.SOURCE_SYSTEM = 'LEGACY_HIS' AND b.SOURCE_SYSTEM = 'LEGACY_HIS' AND a.BRANCH = b.BRANCH)
   AND (SOUNDEX(a.GIVEN_NAME) = SOUNDEX(b.GIVEN_NAME) OR a.MOBILE = b.MOBILE OR a.BIRTH_DATE = b.BIRTH_DATE))
SELECT p.*, S_GIVEN + S_FAMILY + S_BIRTH + S_MOBILE AS SCORE,
       TRIM(CASE S_GIVEN WHEN 25 THEN 'given name exact · ' WHEN 15 THEN 'given name sounds alike · ' ELSE '' END
         || CASE S_FAMILY WHEN 15 THEN 'surname exact · ' WHEN 10 THEN 'surname initial agrees · ' ELSE 'surname differs · ' END
         || CASE WHEN S_BIRTH = 35 THEN 'birth date exact · ' WHEN SWAPPED = 1 THEN 'birth date with day/month swapped · '
                 WHEN S_BIRTH = 10 THEN 'age agrees (no birth date recorded) · ' ELSE '' END
         || CASE S_MOBILE WHEN 30 THEN 'mobile exact' ELSE '' END, ' ·') AS MATCH_REASON
FROM pairs p;

-- 3. link: every record joins the best-scoring partner at or above the threshold; the modern EHR record anchors a person
CREATE OR REPLACE TABLE HOSP_CORE.MPI AS
WITH links AS (
  SELECT A_ID, B_ID, SCORE, MATCH_REASON FROM HOSP_CORE.MATCH_CANDIDATES WHERE SCORE >= 70),
to_modern AS (                                   -- legacy record -> its best modern record
  SELECT L_ID, M_ID, SCORE, MATCH_REASON FROM (
    SELECT CASE WHEN A_SYS = 'LEGACY_HIS' THEN A_ID ELSE B_ID END AS L_ID,
           CASE WHEN A_SYS = 'MODERN_EHR' THEN A_ID ELSE B_ID END AS M_ID, SCORE, MATCH_REASON,
           ROW_NUMBER() OVER (PARTITION BY CASE WHEN A_SYS = 'LEGACY_HIS' THEN A_ID ELSE B_ID END ORDER BY SCORE DESC) AS RN
    FROM HOSP_CORE.MATCH_CANDIDATES WHERE SCORE >= 70 AND A_SYS <> B_SYS) WHERE RN = 1),
legacy_pairs AS (                                -- legacy <-> legacy across branches (Branch A and Branch C registered them twice)
  SELECT A_ID, B_ID, SCORE, MATCH_REASON, ROW_NUMBER() OVER (PARTITION BY A_ID ORDER BY SCORE DESC) AS RN
  FROM HOSP_CORE.MATCH_CANDIDATES WHERE SCORE >= 70 AND A_SYS = 'LEGACY_HIS' AND B_SYS = 'LEGACY_HIS'),
anchor AS (
  SELECT r.RECORD_ID, r.SOURCE_SYSTEM,
         CASE WHEN r.SOURCE_SYSTEM = 'MODERN_EHR' THEN r.RECORD_ID
              ELSE COALESCE(tm.M_ID, tma.M_ID, tmb.M_ID, LEAST(r.RECORD_ID, COALESCE(lpa.B_ID, lpb.A_ID, r.RECORD_ID))) END AS ANCHOR_ID,
         COALESCE(tm.SCORE, lpa.SCORE, lpb.SCORE) AS LINK_SCORE,
         COALESCE(tm.MATCH_REASON, lpa.MATCH_REASON, lpb.MATCH_REASON) AS MATCH_REASON
  FROM HOSP_CORE.PATIENT_RECORDS r
  LEFT JOIN to_modern tm ON tm.L_ID = r.RECORD_ID
  LEFT JOIN legacy_pairs lpa ON lpa.A_ID = r.RECORD_ID AND lpa.RN = 1
  LEFT JOIN legacy_pairs lpb ON lpb.B_ID = r.RECORD_ID AND lpb.RN = 1
  LEFT JOIN to_modern tma ON tma.L_ID = lpa.B_ID          -- transitive: my legacy twin is linked to a modern record
  LEFT JOIN to_modern tmb ON tmb.L_ID = lpb.A_ID)
SELECT 'UP-' || LPAD(DENSE_RANK() OVER (ORDER BY ANCHOR_ID), 6, '0') AS UNIFIED_ID, RECORD_ID, SOURCE_SYSTEM,
       REPLACE(RECORD_ID, '/', '') AS PACS_PATIENT_ID,          -- what the imaging system writes into the DICOM PatientID tag
       ANCHOR_ID, LINK_SCORE, MATCH_REASON
FROM anchor;

-- 4. borderline pairs a human should look at (never auto-linked)
CREATE OR REPLACE VIEW HOSP_CORE.MATCH_REVIEW_QUEUE AS
SELECT A_ID, B_ID, SCORE, MATCH_REASON FROM HOSP_CORE.MATCH_CANDIDATES WHERE SCORE BETWEEN 55 AND 69;

-- HOSP_CORE: the fused, live picture. Every view joins live source data to the master patient index (UNIFIED_ID).
-- Rule learned the hard way on 2026.2.0-nano.3: an aggregate with NO group key (or a GROUP BY expression) over a
-- UNION ALL of virtual-schema views aborts the session (assert in querycreationvisitor.cpp). Always GROUP BY a column.

-- The safety check: a CURRENT order (draft or active, any system) for a drug in a class the patient is allergic to,
-- with the allergy recorded in ANY system. KNOWN_WHERE_PRESCRIBED says whether the prescribing system could have seen it.
CREATE OR REPLACE VIEW HOSP_CORE.ALLERGY_CONFLICTS AS
SELECT o.UNIFIED_ID, o.ENCOUNTER_ID, o.SOURCE_SYSTEM AS PRESCRIBED_IN, o.RECORD_ID AS PRESCRIBED_UNDER, o.DRUG, o.DOSE, o.ORDER_STATUS,
       o.DRUG_CLASS, a.ALLERGY_AS_RECORDED, a.SEVERITY, a.SOURCE_SYSTEM AS ALLERGY_RECORDED_IN, a.RECORD_ID AS ALLERGY_RECORD_ID,
       CASE WHEN a.RECORD_ID = o.RECORD_ID THEN TRUE ELSE FALSE END AS KNOWN_WHERE_PRESCRIBED
FROM HOSP_CORE.MEDICATIONS o
JOIN HOSP_CORE.ALLERGIES a ON a.UNIFIED_ID = o.UNIFIED_ID AND a.DRUG_CLASS = o.DRUG_CLASS
WHERE o.ORDER_STATUS IN ('draft', 'active');

-- 30-day readmission, the certified definition: an inpatient admission within 30 days of the same PERSON's previous
-- inpatient discharge, at any branch, in any system. VISIBLE_TO_ONE_SYSTEM: the previous stay is under the same record id,
-- i.e. the branch system on its own would have counted it.
CREATE OR REPLACE VIEW HOSP_CORE.READMISSIONS_30D AS
WITH ip AS (
  SELECT UNIFIED_ID, RECORD_ID, ENCOUNTER_ID, SOURCE_SYSTEM, BRANCH, ADMIT_DATE, DISCHARGE_DATE, DIAGNOSIS,
         LAG(DISCHARGE_DATE) OVER (PARTITION BY UNIFIED_ID ORDER BY ADMIT_DATE, ENCOUNTER_ID) AS PREV_DISCHARGE,
         LAG(RECORD_ID) OVER (PARTITION BY UNIFIED_ID ORDER BY ADMIT_DATE, ENCOUNTER_ID) AS PREV_RECORD_ID,
         LAG(BRANCH) OVER (PARTITION BY UNIFIED_ID ORDER BY ADMIT_DATE, ENCOUNTER_ID) AS PREV_BRANCH,
         LAG(ENCOUNTER_ID) OVER (PARTITION BY UNIFIED_ID ORDER BY ADMIT_DATE, ENCOUNTER_ID) AS PREV_ENCOUNTER_ID
  FROM HOSP_CORE.ENCOUNTERS WHERE ENCOUNTER_CLASS = 'inpatient')
SELECT UNIFIED_ID, ENCOUNTER_ID, BRANCH, SOURCE_SYSTEM, ADMIT_DATE, DIAGNOSIS, PREV_ENCOUNTER_ID, PREV_BRANCH, PREV_DISCHARGE,
       DAYS_BETWEEN(ADMIT_DATE, PREV_DISCHARGE) AS DAYS_SINCE_DISCHARGE,
       CASE WHEN PREV_RECORD_ID = RECORD_ID THEN TRUE ELSE FALSE END AS VISIBLE_TO_ONE_SYSTEM
FROM ip
WHERE PREV_DISCHARGE IS NOT NULL AND DAYS_BETWEEN(ADMIT_DATE, PREV_DISCHARGE) BETWEEN 0 AND 30;

-- Usage: WHERE q.NOTE_ID = '<note>' ; the text of each note stays in its source system.

FROM HOSP_CORE.NOTE_INDEX n JOIN HOSP_CORE.MPI m ON m.RECORD_ID = n.RECORD_ID;

-- HOSP_GOV: the governed semantic views:
-- definitions live in the view (COMMENT IS), rows are filtered by CURRENT_USER through ACCESS_MAP, and an AI client
-- connected through the Exasol MCP server as a named user can read these views and nothing else.
-- New here: PHI masking. PHI_LEVEL 'FULL' (treating clinician) sees identity; 'MASKED' (analyst) sees a pseudonym.
CREATE SCHEMA IF NOT EXISTS HOSP_GOV;

CREATE OR REPLACE TABLE HOSP_GOV.ACCESS_MAP (USER_NAME VARCHAR(128), BRANCH VARCHAR(3), PHI_LEVEL VARCHAR(6));
INSERT INTO HOSP_GOV.ACCESS_MAP VALUES
  ('SYS', '*', 'FULL'),                    -- the demo console
  ('HOSP_DR_BRB', 'BRB', 'FULL'),         -- treating physician, Branch B: own branch's patients, full history from every branch
  ('HOSP_QUALITY_ANALYST', '*', 'MASKED'); -- quality & readmissions analyst: every branch, no identities

-- One row per person, built from the native master patient index (fast, no source round trip).
CREATE OR REPLACE VIEW HOSP_CORE.PATIENT_SUMMARY AS
SELECT m.UNIFIED_ID,
       COALESCE(MAX(CASE WHEN r.SOURCE_SYSTEM = 'MODERN_EHR' THEN r.NAME_AS_RECORDED END),
                MAX(INITCAP(r.GIVEN_NAME) || ' ' || r.FAMILY_NAME)) AS PATIENT_NAME,
       MAX(r.SEX) AS SEX, MAX(r.BIRTH_DATE) AS BIRTH_DATE, MAX(r.MOBILE) AS MOBILE,
       COUNT(*) AS RECORDS, GROUP_CONCAT(DISTINCT r.SOURCE_SYSTEM ORDER BY r.SOURCE_SYSTEM SEPARATOR ' + ') AS SYSTEMS,
       GROUP_CONCAT(DISTINCT r.BRANCH ORDER BY r.BRANCH SEPARATOR ', ') AS BRANCHES,
       GROUP_CONCAT(r.RECORD_ID ORDER BY r.SOURCE_SYSTEM DESC SEPARATOR ', ') AS RECORD_IDS
FROM HOSP_CORE.MPI m JOIN HOSP_CORE.PATIENT_RECORDS r ON r.RECORD_ID = m.RECORD_ID
GROUP BY m.UNIFIED_ID;

-- Who may see whom: patients registered at one of the caller's branches ('*' = all). Not granted to anyone.
CREATE OR REPLACE VIEW HOSP_GOV.VISIBLE_PATIENTS AS
SELECT DISTINCT m.UNIFIED_ID, a.PHI_LEVEL
FROM HOSP_CORE.MPI m JOIN HOSP_CORE.PATIENT_RECORDS r ON r.RECORD_ID = m.RECORD_ID
JOIN HOSP_GOV.ACCESS_MAP a ON a.USER_NAME = CURRENT_USER AND (a.BRANCH = '*' OR a.BRANCH = r.BRANCH);

CREATE OR REPLACE VIEW HOSP_GOV.PATIENTS AS
SELECT p.UNIFIED_ID,
       CASE WHEN v.PHI_LEVEL = 'FULL' THEN p.PATIENT_NAME ELSE 'Patient ' || SUBSTR(HASH_SHA1(p.UNIFIED_ID), 1, 6) END AS PATIENT_NAME,
       p.SEX, CASE WHEN v.PHI_LEVEL = 'FULL' THEN p.BIRTH_DATE END AS BIRTH_DATE, YEAR(p.BIRTH_DATE) AS BIRTH_YEAR,
       YEARS_BETWEEN(CURRENT_DATE, p.BIRTH_DATE) AS AGE, CASE WHEN v.PHI_LEVEL = 'FULL' THEN p.MOBILE END AS MOBILE,
       p.RECORDS, p.SYSTEMS, p.BRANCHES
FROM HOSP_CORE.PATIENT_SUMMARY p JOIN HOSP_GOV.VISIBLE_PATIENTS v ON v.UNIFIED_ID = p.UNIFIED_ID
COMMENT IS 'Governed data product. Grain: ONE ROW PER PERSON (UNIFIED_ID from the master patient index), however many records the branches hold. Rows are limited to the patients the caller may see; for a MASKED caller PATIENT_NAME is a pseudonym and BIRTH_DATE and MOBILE are NULL. SYSTEMS lists where this person has records (LEGACY_HIS = Branch A/Branch C HIS, MODERN_EHR = Branch B/Branch C EHR).';

CREATE OR REPLACE VIEW HOSP_GOV.ENCOUNTERS AS
SELECT e.UNIFIED_ID, e.ENCOUNTER_ID, e.SOURCE_SYSTEM, e.BRANCH, e.ENCOUNTER_CLASS, e.DEPARTMENT, e.ADMIT_DATE, e.DISCHARGE_DATE,
       e.LENGTH_OF_STAY, e.STATUS, e.DX_CODE, e.DIAGNOSIS
FROM HOSP_CORE.ENCOUNTERS e JOIN HOSP_GOV.VISIBLE_PATIENTS v ON v.UNIFIED_ID = e.UNIFIED_ID

CREATE OR REPLACE VIEW HOSP_GOV.READMISSIONS_30D AS
SELECT r.UNIFIED_ID, r.ENCOUNTER_ID, r.BRANCH, r.SOURCE_SYSTEM, r.ADMIT_DATE, r.DIAGNOSIS, r.PREV_BRANCH, r.PREV_DISCHARGE,
       r.DAYS_SINCE_DISCHARGE, r.VISIBLE_TO_ONE_SYSTEM
FROM HOSP_CORE.READMISSIONS_30D r JOIN HOSP_GOV.VISIBLE_PATIENTS v ON v.UNIFIED_ID = r.UNIFIED_ID
COMMENT IS 'Certified definition of a 30-day readmission: an inpatient admission within 0-30 days of the SAME PERSON''s previous inpatient discharge, at ANY branch, in ANY system. CREATE OR REPLACE VIEW HOSP_GOV.ALLERGY_ALERTS AS

CREATE OR REPLACE VIEW HOSP_GOV.IMAGING_STUDIES AS

COMMENT IS 'Grain: ONE ROW PER IMAGING STUDY in the PACS on Amazon S3 (DICOM header index, read in place). MODALITY: DX/CR = X-ray, CT, MR = MRI. The images stay in S3 (S3_KEY); no pixels pass through the database.';

         LAG(ENCOUNTER_ID) OVER (PARTITION BY UNIFIED_ID ORDER BY ADMIT_DATE, ENCOUNTER_ID) AS PREV_ENCOUNTER_ID
  FROM HOSP_ACCEL.ENCOUNTERS WHERE ENCOUNTER_CLASS = 'inpatient')
SELECT UNIFIED_ID, ENCOUNTER_ID, BRANCH, SOURCE_SYSTEM, ADMIT_DATE, DIAGNOSIS, PREV_ENCOUNTER_ID, PREV_BRANCH, PREV_DISCHARGE,
       DAYS_BETWEEN(ADMIT_DATE, PREV_DISCHARGE) AS DAYS_SINCE_DISCHARGE,
       CASE WHEN PREV_RECORD_ID = RECORD_ID THEN TRUE ELSE FALSE END AS VISIBLE_TO_ONE_SYSTEM
FROM ip
WHERE PREV_DISCHARGE IS NOT NULL AND DAYS_BETWEEN(ADMIT_DATE, PREV_DISCHARGE) BETWEEN 0 AND 30;

-- HOSP_CONSOLE: what the dash-server console needs beyond the HOSP_CORE views. The console runs as the kit's read-only
-- user (MCP_READONLY), which cannot read the DBA audit tables, so the audit log is exposed through a view owned by the

WHERE  s.USER_NAME IN ('HOSP_DR_BRB', 'HOSP_QUALITY_ANALYST') AND a.COMMAND_NAME = 'SELECT'
  AND  a.SQL_TEXT NOT LIKE '/*snapshot execution*/%';
GRANT SELECT ON SCHEMA HOSP_CONSOLE TO MCP_READONLY;
